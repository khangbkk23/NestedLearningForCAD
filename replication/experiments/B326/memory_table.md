**Headline number:** the method-specific state, i.e. column (1) + column (2) of F. M1 did not give `BASE_PORTABLE` (regenerating on Windows gave a different SHA-256 from Linux), so BASE stays counted.
- bf16: 148.3 MB (headline).
- With the M2 int8 archive (no measurable quality change): 135.6 MB (secondary).

BASE is required at inference, like the generator that ReplayCAD does not count (card section 5, item 8). Column (1) is the additional CL state: usable only when BASE (column 2) and the encoder (column 3) are available. It cannot score on its own.

**About the int8 number:**
- It is the tensor payload (int8 + fp16 scales), without the `torch.save` container.
- Job M2 scored an in-RAM dequantised copy built from exactly the stored tensors.
- Two paths are untested: reloading `archive_int8.pt` from file and dequantising it, and resuming training from the int8 archive. Claims about file-based deployment or resume need their own check.

**Growth with tasks:** the archive grows linearly, 1.70 MB/task in bf16 and 0.85 MB/task in int8. UCAD preallocates for 15 tasks; CADIC is constant.

**C's policy is larger than F's**, because C's warm checkpoint also stores the fixed initialisation `phi` (3.39 MB); F stores only λ.

**Dtype:** F is counted in bf16; most literature numbers are inferred at FP32 (column "Source of the number"). For a same-dtype comparison use the fp32 row of F; that row only doubles the archive, BASE and encoder are counted as in the other rows.

**Scope of the comparison:**
- The literature table counts only the persistent CL state, not the frozen backbone, so it compares with column (1) only. The self-reported / inferred label is kept in "Source of the number".
- Column (2) has no counterpart in the literature (other methods use a pretrained backbone). It must be reported next to column (1), neither merged nor dropped.
