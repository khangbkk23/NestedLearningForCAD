## 2. Three directions

### M3: report memory in three columns (no GPU)

Question: counted correctly, how much does F store compared with the literature? Columns: (1) CL state = archive +
policy, directly comparable with the literature; (2) BASE, method-specific and frozen, no counterpart in the literature
(other methods use a pretrained backbone), reported separately, neither merged into (1) nor hidden; (3) public
backbone (encoder), reported for completeness, not compared. Output: [memory_table.md](memory_table.md), generated by
`replication/scripts/b326_memory_table.py` (stdlib, CPU). Finding while building it: most literature numbers are
inferred at **FP32** while F is counted in bf16; at the same dtype, column (1) of F is **50.9 MB**, above UCAD (24.4)
and CADIC 10k (30.7). F is level with them only in bf16, and below them in int8 (M2).

### M2: int8 archive (GPU scoring job, no training)

Question: does storing the archive in int8 keep detector quality?

- Quantisation (fixed in advance): each expert and site has A ∈ ℝ^{8×in} and B ∈ ℝ^{out×8}; symmetric int8 per rank
  component, A per row (8 scales), B per column (8 scales), scales in fp16. At scoring, dequantise and call Khang's
  `nar_lite_01.expert_grids` unchanged; only the archive transform is new.
- Expected bytes: 15 × 847,872 parameters × 1 byte + 15 × 34 × 16 scales × 2 bytes ≈ **12.73 MB** versus 25.44 MB.
- Inputs: the sealed `stage15.pt` of arm F at seeds 2711 (job Q, Khang's BASE), 2712 and 2713 (job R, T4 BASE). No
  retraining.
- Normal-image fidelity gate: relative mean absolute error of the min-over-experts map, int8 versus original, on the 4
  EVAL train/good images per category used by `nar_lite_01.fidelity`; threshold ≤ 0.01 (stricter than bf16's 0.05).
  If the gate fails the run is still scored but the label is capped at `INT8_LOSSY`.
- Rules (Δ = int8 − bf16, same checkpoint, same test features, readout A1):
  - `INT8_LOSSLESS`: at all three seeds |Δ Pixel AP| ≤ 0.002 and |Δ Image AUROC| ≤ 0.002, and the gate passes;
  - `INT8_WITHIN_0005`: otherwise, at all three seeds Δ Pixel AP ≥ −0.005 and Δ Image AUROC ≥ −0.005, and the gate
    passes (a gain also counts);
  - `INT8_LOSSY`: otherwise.
  The thresholds are small on purpose: both sides use the same checkpoint and test features, so only quantisation
  differs. The bf16 reference is re-scored in the same job.

### M1: BASE from a seeded CPU generator (GPU job with training)

Question: can BASE (122.9 MB) be replaced by a seed and a code hash without losing quality?

Why: B325 job Q showed that `model_new(2711)` on a T4 gives a BASE very different from Khang's (max abs difference
0.0596, the size of the weights), so CUDA generation is not reproducible across machines (GPU and PyTorch version
both differ there).

Change (a change of initialisation, stated explicitly): new function `base_from_seed(seed)` in the B326 driver, with
Khang's code untouched. Build `SingleStreamDecoder` on the CPU; initialise in the module order and with the
distributions of `O.init_trainable` (`trunc_normal_` std 0.01 cut at ±0.03 for Linear weights, bias 0, LayerNorm 1/0),
with randomness from a dedicated CPU `torch.Generator` seeded with s; then load it as a normal BASE. Same
distribution, different random source.

- **M1a, reproducibility.** Canonical SHA-256 over key names and fp32 tensor bytes in `state_dict` order (not
  `torch.save` bytes). BASE identity = seed, PyTorch version, generator algorithm (CPU mt19937), generator code hash.
  Generated with `ATEN_CPU_CAPABILITY=default`, GPU hidden. In the job: two separate processes per seed.
  `BASE_PORTABLE` if the SHA-256 is identical on at least two machine types (different CPU vendor/ISA or OS);
  `BASE_SAME_MACHINE_ONLY` if identical only on one machine; `BASE_NOT_REPRODUCIBLE` if not even that.
- **M1b, quality.** Train F with the CPU BASE at seeds 2712 and 2713 and, in the same job, retrain F with the T4 BASE
  saved by job R. Δ = F(CPU BASE) − F(T4 BASE), same job, final Pixel AP, A1. `BASE_FROM_SEED_OK`: |mean Δ| < 0.005
  and |Δ| < 0.010 at each seed (worded as "no change detected at n = 2", not "no loss"); `BASE_FROM_SEED_WORSE`:
  Δ ≤ −0.010 at both seeds; otherwise `BASE_FROM_SEED_MIXED`. F(T4 BASE, this job) − F(T4 BASE, job R) is reported as a
  rerun noise reference.
- BASE may be counted as ≈ 0 MB in M3 only with **both** `BASE_PORTABLE` and `BASE_FROM_SEED_OK`.

## 4. Out of scope

No change to γ, rank, sites, steps or readout. No merging of experts (removing the O(T) growth changes the method and
needs its own card). No int4 or other schemes, no scale sweep. No further encoder block cuts. No VisA, no seeds added
after seeing results. Not to be called "nested learning reduces memory": F is not nested learning.

## 5. Revisions before writing code (19 Nov 2026)

Checked and correct: the byte arithmetic (34 Linear layers; BASE 61,425,408 parameters; 847,872 parameters per
expert; int8 archive 12,734,400 bytes); the decoder has only Linear and LayerNorm parameters and `init_trainable`
initialises all of them; training always loads BASE through `model_new(base)`, so the CUDA random stream during
training does not depend on how BASE was produced; the fidelity gate uses exactly 4 EVAL images per category.

1. **M2 inputs.** Each checkpoint needs the BASE it was trained with: 2711 → Khang's `BASE.pt` `dfe6689e…`; 2712 → T4
   BASE `eebf94ce…`; 2713 → T4 BASE `d3f30604…`. SHA-256 of every `stage15.pt` and BASE is checked against the B325
   run records before scoring; paths are explicit in the config, not found by a glob for `BASE.pt`.
2. **M1a details** as in section 2 (canonical SHA, identity, `ATEN_CPU_CAPABILITY=default`, a test asserting with
   `inspect.signature` that `nn.init.trunc_normal_` accepts `generator`).
3. **M3 BASE column:** ≈ 0 MB only with both labels, as above.
4. **Section 3 last row** is an untested projection.
5. **Quantisation spec:** quantise from the sealed fp32 tensors; scale = amax / 127 rounded to fp16 first, q computed
   with that fp16 scale; round half to even, clamp to ±127; a component with amax = 0 gets scale 1 and q = 0;
   dequantise in fp32 then cast; bytes measured on the stored int8 and fp16 tensors; Δ is the final macro value at
   task 15, with max per-category |Δ| reported.
6. **M2 labels:** `INT8_SMALL_LOSS` renamed `INT8_WITHIN_0005` (definition above). Gate stays 0.01; the error of the
   bf16 archive against fp32, measured the same way in the same job, is reported as a noise reference.
7. **M1b framing:** the two BASEs are draws from the same distribution, so M1b mainly measures sensitivity to the
   BASE draw plus rerun noise; hence the within-job T4 retrain.
8. **Fairness against the literature (M3):** same-dtype comparison (column 1 of F at fp32 is 50.9 MB); growth (F
   linear, UCAD preallocated for 15 tasks, CADIC constant); **headline = column (1) + column (2) = 148.3 MB in bf16**
   until M1 succeeds; BASE is required at inference, like the generator ReplayCAD does not count. Column (1) is the
   additional CL state, usable only when BASE and the encoder are available; it cannot score on its own. F warm-starts
   from the last endpoint, which is in the archive, but no job tested resuming training from a stored archive
   (bf16 or int8).
9. **M3 sources:** the B325 records have no `persistent_bytes`; M3 uses only Khang's `hope_s_02` and `nar_lite_01`
   (pinned by text hash) plus architecture arithmetic.

## 6. Implementation (19 Nov 2026)

- Driver `replication/scripts/b326_memory.py`, config `replication/configs/b326.json`, tests
  `replication/tests/test_b326.py`. Gate, feature extraction, training, fidelity, test extraction, scoring and metrics
  call the phases of `replication/scripts/hope_replicate.py`; Khang's functions are used unchanged.
- New phases: `locate` (find the pinned B325 checkpoints and BASEs under the input directories by explicit relative
  paths and check SHA-256); `quantize` (`quantize_archive`, `dequantize_archive`); `int8-gate` (normal-image min-map
  error int8 versus original, threshold 0.01, then Khang's `nar_lite_01.fidelity` on the bf16 checkpoint as a noise
  floor); `metrics-plain` (metrics for a run with a checkpoint but no training records); `cpu-base`
  (`base_from_seed`, `canonical_sha`; asserts every decoder parameter was seed-initialised and the decoder has no
  buffers); labels `label_m2`, `label_m1a`, `label_m1b`.
- **M2 order:** gate → locate → quantize (3 seeds) → int8-gate (lanes) → test extraction bf16 once → score 6 runs →
  metrics (3 workers) → labels.
- **M1 order:** gate → locate → train feature extraction → cpu-base (2 seeds × 2 processes) → train F, one seed per
  GPU, CPU BASE then T4 BASE → fidelity → common precision per seed → test extraction → scoring → metrics (2 workers)
  → labels.
- Time limits: 3.5 h per job (estimates 2.1–2.6 h).
